이 모듈은 원격 데스크톱 스트리밍의 코덱 계층이다. 서버에서 캡처한 D3D11 텍스처를 H.264 로 인코딩하고, 클라이언트에서 그 비트스트림을 다시 D3D11 텍스처로 되돌린다. 양쪽 모두 GPU 메모리를 벗어나지 않는다 — 시스템 메모리로 내려오는 지점은 인코딩된 비트스트림 하나뿐이다.

설계에서 가장 많이 다룬 주제는 지연이 어디서 생기는가였다. "버퍼를 늘리면 안전하다" 같은 직관이 측정과 반대로 나오는 경우가 여러 번 있었고, 그때마다 하네스를 먼저 만들고 숫자를 본 뒤에 코드를 고쳤다.

SDK 를 그대로 쓰지 않은 이유

Video Codec SDK 는 NvEncoderD3D11 같은 래퍼를 제공하지만, 이 파이프라인이 필요로 하는 세 가지가 없다. 비동기 완료 이벤트 기반의 슬롯 회수, 인코딩을 멈추지 않는 런타임 비트레이트 변경, 다른 디바이스가 만든 공유 텍스처를 입력으로 받는 경로. 그래서 nvEncodeAPI 를 직접 호출하는 구현을 따로 썼다.

코드 구조

인코더 6 클래스, 디코더 4 클래스. 스레드를 누가 소유하는지가 배치의 기준이다.

pimpl 한 겹을 둔 이유

D3D11NvEncoder / D3D11NvDecoder 는 거의 전달만 한다. 실제 구현은 _Impl 에 있다. DLL 경계를 넘는 헤더에 nvEncodeAPI.h 나 CUDA 헤더가 새어 나가지 않게 하려는 것이 첫째 이유고, 둘째는 SDK 버전을 올릴 때 사용자 쪽 재컴파일을 강제하지 않기 위해서다.

인코더는 스레드가 둘, 디코더는 하나

대칭으로 만들 수 있었는데 그러지 않았다. NVDEC 파서가 콜백을 cuvidParseVideoData 안에서 동기로 부르기 때문이다 — 디코딩 결과가 나오는 시점이 이미 파서 호출 스레드에 묶여 있어서, 회수 스레드를 따로 두면 할 일이 없다.

반대로 NVENC 는 nvEncEncodePicture 가 즉시 반환하고 완료를 이벤트로 알린다. 그래서 제출과 회수를 나눌 수 있고, 나눠야 제출이 GPU 를 기다리지 않는다. 구조가 다른 것은 SDK 의 모델이 다르기 때문이지 설계 취향이 아니다.

전체 처리 파이프라인

화면 한 장이 서버 GPU 에서 클라이언트 화면까지 가는 길.

단계별로 무슨 일이 일어나는가

  1. 캡처 → 공유 텍스처

    캡처 엔진이 자기 디바이스의 BGRA 슬롯에 데스크톱을 복사한다. 이 텍스처는 KEYEDMUTEX | NTHANDLE 로 만들어져 있어 인코더 디바이스에서 열 수 있다.

  2. 공유 텍스처 → 인코더 BGRA 슬롯

    인코더가 keyed mutex 를 잡고 CopyResource 한 뒤 즉시 놓는다. 이 한 줄이 구조의 전부다 — 이후 작업은 전부 인코더 디바이스 안의 일이라, 드라이버 안에서 얼마나 오래 블로킹하든 캡처 쪽은 영향을 받지 않는다.

  3. BGRA → NV12

    ID3D11VideoProcessor 고정 기능으로 변환한다. BT.709 계수, full range (NOMINAL_RANGE_0_255). 이 선택이 인코더 VUI 와 짝을 이룬다.

  4. NVENC 제출

    nvEncMapInputResource → nvEncEncodePicture. 슬롯마다 완료 이벤트를 달아 보내고 기다리지 않고 돌아온다.

  5. 완료 회수

    별도 스레드가 완료 이벤트를 기다렸다가 nvEncLockBitstream 으로 비트스트림을 복사하고, 슬롯을 먼저 반납한 뒤 앱 콜백을 부른다.

  6. 전송 → 파싱

    앱이 32KB 청크로 쪼개 보낸다. 클라이언트는 받은 덩어리를 그대로 cuvidParseVideoData 에 먹인다.

  7. 디코딩 → 표시

    파서가 같은 스레드에서 세 콜백을 동기 호출한다. 마지막 콜백에서 CUDA 커널이 NV12 를 BGRA 로 바꿔 D3D11 텍스처에 쓰고, CUDA 이벤트를 기록한다. 앱은 AcquireFrame 에서 그 이벤트를 기다렸다가 텍스처를 받는다.

색공간을 명시하는 이유

컨버터가 RGB full range 를 BT.709 로 변환하므로, 인코더도 SPS 의 VUI 에 videoFullRangeFlag = 1 과 BT.709 계수를 명시적으로 적어 보낸다.

적지 않으면 수신측이 추측한다. 대부분의 디코더는 SD 가 아니면 BT.709 로 가정하지만 range 는 limited 로 가정하는 경우가 많아, 검정이 들뜨고 흰색이 회색으로 보이는 증상이 생긴다. 코드 한 줄로 막을 수 있는 종류의 버그다.

동시성 모델

비동기가 세 종류다. 각각 기다리는 주체가 다르고, 그래서 도구도 다르다.

세 가지 비동기

경계무엇이 비동기인가기다리는 도구기다리는 쪽
CPU ↔ CPU제출과 회수가 서로를 기다리지 않는다 원자 카운터 m_pendingFrameCount아무도
CPU ↔ NVENCnvEncEncodePicture 가 즉시 반환 슬롯별 Win32 이벤트완료 스레드

셋을 같은 도구로 풀려고 하면 어느 하나가 과하거나 모자라게 된다. CPU 끼리는 순서만 지키면 되고, GPU 와는 완료를 확인할 방법이 있어야 한다.

어디에 락을 쓰고 어디에 쓰지 않는가

이 모듈은 락을 전부 없앤 설계가 아니다. 판단 기준은 하나다 — 기다리는 것이 목적이면 커널 객체, 기다리면 지는 것이면 원자 연산.

큐에 락을 쓰는 것이 타협이 아닌 이유

유입 큐는 워커를 재우는 것이 기능이다. 프레임이 없을 때 스핀하면 32 코어 중 하나를 100% 태우면서 아무것도 하지 않는다. SleepConditionVariableSRW 는 그 대기를 커널에 맡긴다.

그리고 이 큐는 초당 60회만 돈다. 락 획득 비용은 위 측정에서 0.1 µs 수준이고, 60 fps 예산의 0.0006% 다. 락을 쓰면 안 되는 자리와 써도 되는 자리를 나누는 것이 락을 없애는 것보다 중요하다.

큐 슬롯의 상태 기계

보통의 큐는 "모든 항목이 처리된다" 를 전제한다. 실시간 인코딩에서는 그게 틀린 전제다 — 인코더가 밀렸으면 중간 프레임은 처리되면 안 된다. 그래서 EnqueueFrame 이 매번 DropQueuedFrames_NoLock() 을 먼저 부르고, queuedCount 를 항상 1 로 덮어쓴다.

이 성질 덕분에 어느 시점에도 QUEUED 1 개 + HELD 1 개만 존재하고, 슬롯 2 개면 충분하다. 버려진 프레임은 반납 콜백으로 앱에 돌아가 캡처 슬롯이 풀린다 — 큐 형태를 유지한 이유가 이 반납 경로다.

정직하게 — 이 모듈에서 절대량은 작다

인코드 경로의 원자 읽기는 프레임당 십수 회다. 14.03 사이클 × 15 ≈ 210 사이클, 4.29 GHz 에서 약 49 ns. 60 fps 예산 16.7 ms 의 0.0003% 이고, 이 파이프라인의 실제 지연 3.7 ms 와 비교해도 무의미한 크기다.

그러니 이 치환의 값어치는 이 모듈의 프레임 예산을 아낀 것이 아니다. 의미가 큰 곳은 초당 수십만 회 도는 네트워크 엔진의 핫 경로이고, 여기서는 "읽기에 쓰기 명령을 쓰지 않는다" 는 규칙의 일관성이 얻은 것에 가깝다.

반면 캐시 라인 분리(9.3배)와 게이트 구간 축소는 절대량으로도 의미가 있었다. 특히 게이트는 지연의 구조에서 보듯 렌더러 점유율에 비례해 지연을 4.8배까지 밀어올린다 — 같은 "동기화 비용" 이라도 자릿수가 다르다.

왜 슬롯을 콜백보다 먼저 반납하는가

이 변경은 성능 개선이 아니다. 측정해 보니 처리량은 오차 범위였고 포화 지연은 오히려 올라갔다(2000 µs 콜백에서 6.33 → 8.02 ms).

이유가 분명했다. 이전에는 콜백 동안 슬롯이 묶여 파이프라인이 설정된 깊이 4 를 다 쓰지 못했고, 그 우연한 스로틀이 지연을 낮추고 있었다. 지금은 깊이 4 를 온전히 쓴다 — 4 / 488 fps = 8.2 ms 로 Little's Law 와 일치한다.

그래도 이 구조를 유지한다. 인코더 슬롯 점유 시간이 앱 콜백 시간에 의존하지 않게 되기 때문이다. 정상 상태 측정으로는 안 보이는 테일 이벤트 — 힙 경합이나 페이지 폴트로 콜백이 드물게 수 ms 튀는 경우 — 가 슬롯 고갈로 번지지 않는다. 지연을 낮추고 싶으면 우연한 스로틀에 기대는 대신 encodeSlotCount 를 줄이는 것이 맞다.

비트스트림 회수: 게이트는 NVENC 호출에만

한때 ReadEncodedBitstream 에서 게이트를 통째로 걷어냈다. 이 함수가 만지는 것은 nvEncCreateBitstreamBuffer 로 받아 둔 NVENC 자체 버퍼뿐이고 등록된 D3D11 리소스가 호출 경로에 없으니 immediate context 와 무관하다고 봤다. 틀린 판단이었다.

디버그 빌드 서버가 스트리밍 중 간헐적으로 죽었다(예외 0x87D, 수 회에 한 번). 예외를 잡는 진단 핸들러로 스택을 받아 보니 완료 스레드의 nvEncLockBitstream 안에서 드라이버가 ID3D11DeviceContext::DecoderExtension 을 부르고 있었고, 같은 순간 엔코드 스레드도 그 컨텍스트를 쓰고 있었다. 디버그 레이어의 CORRUPTED_MULTITHREADING 이다. NVENC 가 D3D11 디바이스를 받으면 자기 버퍼만 만지는 것처럼 보이는 호출도 그 디바이스의 컨텍스트를 쓴다. 릴리스 빌드였다면 죽지 않고 조용히 메모리를 깼을 것이다.

그래서 nvEncLockBitstream / nvEncUnlockBitstream 호출은 게이트 안으로 되돌렸다. 원래 걷어낸 이유 — 이 구간이 가장 길다 — 는 호출 사이의 재할당과 패킷 memcpy 때문이었으므로 그것들은 게이트 밖에 남겼다. 비동기 경로는 완료 이벤트를 기다린 뒤에 Lock 하므로 게이트 안에서 기다릴 일도 없다.

B 프레임을 지원하지 않는다고 명시한다

if (nvStatus == NV_ENC_ERR_NEED_MORE_INPUT) {
    // 슬롯 하나 = 출력 하나를 가정한 링 구조다.
    // 여기서 true 를 돌려주면 그 슬롯의 completion event 가 영원히
    // signal 되지 않아 완료 스레드가 20초 뒤 세션을 포기한다.
    // 조용히 매달리는 대신 즉시 실패한다.

frameIntervalP = 1 과 lookahead 없음 설정에서는 발생하지 않는다. 그래도 방어를 넣은 것은 설정이 바뀌었을 때 증상이 "20초 뒤 정지" 로 나타나는 것을 막기 위해서다. 지원하지 않는 조합은 빨리, 이유와 함께 실패해야 한다.

슬롯 링과 두 스레드

제출과 회수를 분리하고, 그 사이를 원자 카운터 하나로 잇는다.

이벤트 두 개의 수명을 스레드와 분리했다

m_allSlotsFreeEvent 와 m_frameSubmittedEvent 는 인코더가 소유하고 Initialize 에서 만들어 Destroy 끝에서 닫는다. 완료 스레드와 함께 만들고 지우면 SubmitFrame(인코드 스레드)과 WaitForPendingFrames(임의 스레드)가 이미 닫힌 핸들을 읽는 창이 생긴다.

같은 이유로 SubmitFrame 은 완료 스레드 객체 포인터를 역참조하지 않는다. 그 포인터는 DestroyEncodeCompletionThread 가 지우므로 use-after-free 창이 된다. 이벤트만 만진다.

ResetEvent 순서 하나가 만드는 창

pendingCount++;                       먼저 올리고

ResetEvent(allSlotsFreeEvent);        그 다음에 리셋
if (GetPendingFrameCount() == 0)       리셋 직후 다시 확인
    SetEvent(allSlotsFreeEvent);       그 사이에 드레인이 끝났으면 되돌린다

올리기 전 값으로 판단하면, 그 사이에 완료 스레드가 pending 을 0 으로 만들며 SetEvent 한 것을 되돌리지 못해 pending > 0 인데 이벤트는 SET 인 상태가 남는다. 그러면 WaitForPendingFrames 가 아직 남은 프레임을 두고 곧바로 통과한다.

배리어를 하나 지운 이유

페이로드를 먼저 쓰고 시퀀스를 올린다. InterlockedIncrement 가 full barrier 라 이 순서는 컴파일러도 CPU 도 뒤집지 못한다 — 소비자가 시퀀스를 본 시점에 timestamp 는 반드시 보인다. 예전에 있던 명시적 MemoryBarrier 는 중복이었다.

단, 텍스처 내용은 이 배리어의 관할이 아니다. 그쪽은 GPU 가 쓰므로 CUDA 이벤트와 AcquireFrame 의 cuEventSynchronize 가 담당한다. CPU 배리어와 GPU 완료는 서로 다른 문제다.

GPU 대기를 AcquireFrame 으로 미룬 것에 대해

OnPictureDisplay 는 스트림을 동기화하지 않고 CUDA 이벤트만 기록하고 나온다. 대기는 프레임이 실제로 필요한 AcquireFrame 이 한다.

다만 이 비동기가 실제로 겹쳐지지는 않는다. DecodeThread 가 Parse 직후 같은 반복에서 AcquireFrame 을 부르므로, 방금 넣은 그 프레임을 곧바로 기다리게 된다. 미룬 거리는 사실상 0 이다.

그래도 이 모양이 맞다고 판단했다. 겹치게 하려면 드레인을 한 반복 뒤로 물려야 하는데 (N 을 파싱하면서 N-1 을 꺼내는 식), 그 대가가 60fps 에서 16.7 ms 다. 아끼는 쪽은 QHD 변환 커널과 device-to-device 복사라 1 ms 안쪽이다. 저지연이 목적인 파이프라인에서 그 거래는 방향이 반대다. 즉 이 비동기 구조가 버는 것은 처리량이 아니라, CPU 가 불필요하게 블로킹하지 않는 것뿐이다.

직관이 세 번 틀렸고, 측정이 세 번 다 이유를 알려줬다.

1. 슬롯을 늘리면 안전해지는 게 아니라 느려진다

포화 상태에서 지연 = 깊이 ÷ 처리량 이 거의 정확히 맞는다. 처리량은 깊이 2~8 에서 741/735/738 로 사실상 평평하다. 즉 저지연 목적이면 깊이 2 가 8 보다 4배 유리하고 처리량 손실은 0 이다. "버퍼 많을수록 안전" 이라는 직관과 정반대다.

대신 깊이가 얕으면 일시적 스톨을 흡수하지 못해 프레임을 더 빨리 버린다. 원격 조작 용도라면 10 ms 늦게 도착하는 것보다 버리는 게 낫다는 판단으로 얕은 쪽을 골랐다.

2. sync 가 async 보다 빠른 게 아니다

비포화 상태(60 fps)에서 sync p50 3.691 ms, async p50 3.682 ms — 동일하다. async 는 처리량 여유를 22% 더 주면서(741 vs 604) 지연 손실이 없다. 비동기 구조의 값어치는 "빠름" 이 아니라 여유다.

이건 코드로 고칠 수 없다. 배포 환경 설정 사항으로 분류하고 문서에 남겼다 — 전원 관리 모드 "최대 성능 우선", 또는 nvidia-smi -lgc 로 클럭 하한 고정. 동시에 대역폭이 병목이라는 뜻이므로, 프레임당 여분의 복사를 줄이는 개선의 기대 효과가 다운클럭 상태에서 오히려 더 커진다는 것도 같이 확인했다.

원인은 인코더가 게이트를 오래 잡아서가 아니다. 경합 스레드가 게이트를 얻기까지 기다린 최대 시간은 0.2~1.6 ms 에 그쳤다. 반대로 인코더가 프레임당 게이트를 6 회 요구하고, 그 매 회가 렌더러의 점유 시간만큼 밀린다.

구조적 해답은 명확하다 — 인코딩용 디바이스를 분리하고 공유 텍스처로 넘기면 인코드 경로에 게이트가 아예 필요 없어진다. 서버는 이미 그 구조다. 렌더와 디코드를 함께 하는 클라이언트 쪽이 남은 과제다.

그래서 비트스트림 링버퍼 + 디스패치 스레드를 만들지 않기로 했다. 측정 없이 추가했다면 복잡도만 늘었을 구조다. 콜백이 밀리초 단위로 무거워지거나 뷰어가 수십 단위로 늘면 다시 검토한다는 조건을 같이 적어 뒀다.

최적화 기법

효과를 숫자로 확인한 것만.

VBV 를 1 프레임으로 고정

ApplyRateControlConfig

프리셋 기본 VBV 는 프리셋 자신의 비트레이트 기준으로 계산돼 있어서, averageBitRate 만 덮어쓰면 둘이 어긋난 채 남는다. 저지연에서는 1 프레임 분량이 정석이다.

효과가 지연이 아니라 프레임 크기 분포에서 드러났다 — 최대/평균 비가 4.62 → 2.75. 큰 프레임은 전송이 늦어지므로 실제로는 네트워크 쪽 지연을 줄인다.

Intra refresh

ApplyInitOnlyConfig

주기적 IDR 대신 매 프레임의 일부 띠만 intra 로 인코딩해 60 프레임에 한 바퀴 돌린다. 600 프레임에서 키프레임 이벤트가 10 회 → 1 회로 줄었다.

SDK 제약이 까다로웠다 — gopLength 가 NVENC_INFINITE_GOPLENGTH 가 아니면 intra refresh 가 조용히 무시된다. idrPeriod 도 같이 무한으로 둬야 드라이버가 IDR 을 끼워넣지 않는다. 끄는 경우에도 gopLength 와 idrPeriod 를 일치시켜야 하는데, 다르면 IDR 만큼 크면서 진입점은 못 되는 I 프레임이 중간에 낀다.

키프레임 이벤트 10 → 1

디바이스 분리 + 공유 텍스처 입력

RegisterSharedInputPool · StageFrameFromSharedSlot

캡처와 인코더가 같은 디바이스를 쓰면 게이트 하나를 두 스레드가 다툰다. 인코더가 그 게이트를 쥔 채 nvEncMapInputResource 안에서 드라이버 대기에 들어가면 캡처가 영원히 멈춘다. QHD 60fps 에서 실제로 교착했다.

공유 핸들은 RegisterSharedInputPool 에서 한 번만 열어 둔다. 매 프레임 OpenSharedResource1 하는 것은 그 자체가 드라이버 왕복이다. keyed mutex 를 잡고 있는 구간은 CopyResource + Flush 하나뿐이다.

ReadEncodedBitstream · OnPictureDisplay

완료 스레드가 게이트를 잡는 구간 중 가장 길었던 비트스트림 회수에서 게이트를 NVENC 호출 두 개로 좁혔다. 재할당과 패킷 memcpy 는 게이트 밖이다. 통째로 걷어냈던 적이 있는데, 드라이버가 Lock 안에서 컨텍스트를 써서 디버그 레이어가 멀티스레드 충돌로 프로세스를 죽였다.

디코더 쪽은 반대로 CUDA-D3D11 interop 구간이라 게이트가 필요하지만, 커널 실행과 memcpy 는 스트림에 얹는 비동기 명령이라 오래 잡지 않는다.

원칙 셋

  1. 단발성 유실로 스레드를 끝내지 않는다. 완료 스레드가 한 번의 실패로 종료하면 파이프라인이 조용히 영구 정지한다. 유실은 흘려보내고 연속 누적될 때만 포기한다.
  2. 포기할 때도 대기자를 풀어 준다. AbortPendingFrames 는 Unmap 을 시도하지 않고 (NVENC 가 아직 슬롯을 쥐고 있을 수 있다) 장부만 비운 뒤 allSlotsFreeEvent 를 세운다. 그래야 종료가 20초 타임아웃에 매달리지 않는다.
  3. 지원하지 않는 조합은 빨리 실패한다. EncodeThread 는 동기 모드 인코더를 거절한다 — 아무도 출력을 회수하지 않아 pending 이 차오른 뒤 조용히 멈추기 때문이다. 이유를 로그에 적고 false 를 돌려준다.

장애를 재현하는 훅

DebugFailNextOutputs(n) 은 다음 n 번의 비트스트림 회수를 강제로 실패시킨다. 복구 경로는 재현할 수 없으면 검증할 수 없다는 이유로 넣었다. 실제로 이 훅으로 "3회 복구 후 4회째 상한 도달" 까지 상위 앱에서 확인했다.

트레이드오프와 한계

고르지 않은 것들, 그리고 남은 것.

의도적으로 포기한 것

  • B 프레임 / lookahead — 슬롯 하나 = 출력 하나 가정이 깨진다. 지원하려면 "출력 없는 제출" 을 표현하는 모델이 먼저 필요하다. 저지연 용도에선 어차피 쓰지 않는다.
  • H.265 / AV1 — H.264 고정이다. 코덱 선택을 설정으로 빼는 대신 한 코덱에서 VUI·GOP·VBV 를 정확히 맞추는 쪽에 시간을 썼다.
  • 프레임 순서 보장 — 유입 큐가 latest-only 다. 밀리면 중간 프레임이 사라진다. 녹화용이라면 큐 정책을 바꿔야 한다.
  • 디코더 런타임 재설정 — 디코더는 해상도를 스트림에서 읽으므로 설정할 것이 없다. 해상도 변경은 OnVideoSequence 에서 자동 처리한다.

남아 있는 것

  • 클라이언트 쪽 게이트 경합 — 렌더와 디코드가 같은 디바이스를 쓴다. 서버처럼 분리하면 해결되지만, 디코더 출력을 렌더러가 바로 써야 해서 구조가 더 복잡하다.
  • 인코더 Faulted 에서 자력 복구 불가 — 상위 앱이 Destroy/Initialize 로 재생성한다. 그쪽에 재생성 횟수 상한(60초에 3회)을 둬서 무한 재생성 루프를 막았다.
  • 프레임당 풀프레임 복사 1회 — 공유 텍스처 → BGRA 슬롯 복사(1080p 기준 8.3 MB). 대역폭이 병목인 다운클럭 상태에서 특히 아깝다. 제거하려면 NVENC 가 공유 텍스처를 직접 등록할 수 있어야 하는데, keyed mutex 보유 구간이 인코딩 전체로 늘어나 애초에 없애려던 교착이 돌아온다.

이 모듈에서 얻은 것

가장 크게 배운 것은 측정 하네스를 먼저 만드는 것의 값어치였다. "버퍼를 늘리면 안전하다", "sync 가 더 빠르다", "콜백이 무거우면 디스패치 스레드가 필요하다" — 셋 다 그럴듯했고 셋 다 틀렸다. 숫자를 보지 않았다면 세 가지 최적화를 전부 잘못된 방향으로 했을 것이다.

두 번째는 실패의 등급을 나누는 일이다. 프레임 한 장 유실과 세션 포기를 같은 코드로 다루면, 복구 가능한 상황에서 죽거나 복구 불가능한 상황에서 조용히 얼어붙는다. 둘을 나누는 기준을 "슬롯을 안전하게 회수할 수 있는가" 하나로 정한 뒤에야 모든 실패 경로가 제자리를 찾았다.
