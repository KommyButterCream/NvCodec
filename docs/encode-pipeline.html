Part I · NvCodec · NvEncode · async pipeline

How a BGRA frame becomes an H.264 packet

Three threads, one ring of slots, six gate acquisitions per frame. This traces the asynchronous path end to end, then shows the single edge that changes in synchronous mode. Part II 는 그 패킷이 다시 텍스처가 되는 경로다.

Producer (capture) EncodeThread EncodeCompletionThread holds the context gate

앱이 만지는 것

DLL 이 내보내는 클래스는 넷뿐이다 — D3D11NvEncoder, EncodeFrameQueue, D3D11NvDecoder, DecodeFrameQueue. 아래 나오는 스레드들은 전부 코덱이 내부에서 소유하고, NVENC 와 CUDA 헤더는 밖으로 새지 않는다. 

D3D11NvEncoder encoder;
encoder.Initialize(device, config, gate);
encoder.SetEncodedPacketCallback(OnPacket, this);  // 결과는 여기로 온다

EncodeFrameQueue queue;
queue.Initialize(2, OnReleaseSourceFrame, this);
encoder.StartEncodeThread(&queue);                 // 큐 펌프 가동

queue.EnqueueLatest(handle, forceKeyFrame);        // 프레임 투입
// ...
encoder.Destroy();                                 // 펌프도 같이 멈춘다

동기 인코딩은 StartEncodeThread 를 부르지 않고 PrepareFrameForEncode + DoEncode 를 직접 돌린다. 섹션 07 에서 그 차이를 다룬다.

01

The slot is the unit of everything

The encoder allocates encodeBufferCount slots. A slot number is not an index into one array — it indexes eight parallel arrays at once. Grasp this and the rest of the pipeline is bookkeeping.

02

Two counters chase each other

m_inputSequence and m_outputSequence are monotonic counters — they are never wrapped. Wrapping happens only where a slot is needed, in GetInputSlotIndex() and GetOutputSlotIndex(). Their difference is the number of frames NVENC still owes us.

03

Three threads, two handoffs

No thread polls another. Each handoff is a specific kernel object, and both were moved to the encoder's own lifetime so a thread teardown cannot invalidate a handle another thread is about to read.

04

Submit path — four gate acquisitions

Everything below runs on the EncodeThread. The producer's texture is copied into the pipeline immediately, which is what lets the queue slot go back to the capture engine before encoding has even started.

05

Drain path — the slot is freed before your callback

Everything below runs on the EncodeCompletionThread inside ProcessOneOutput. The ordering at the end is deliberate: the slot goes back into rotation before the app callback runs, so however long broadcasting takes, it never adds to encoder slot occupancy.

06

Where each failure goes

The distinction that matters: after the completion event fires, the hardware is done and the slot can be reclaimed, so a failure costs one frame. Before it fires, NVENC still owns the slot and there is nothing safe to do but give up the session.

Faulting is observable by design. EnterFaultedState clears m_acceptFrames, zeroes the pending bookkeeping so no waiter hangs on the 20-second timeout, and fires the error callback exactly once. From then on CanSubmitFrame() is deterministically false, so the app sees a hard stop instead of frames vanishing. Recovery is Destroy() then Initialize().
07

Synchronous mode changes exactly one thing

Passing enableAsyncPipeline = false removes the completion thread. Nobody else is added — the calling thread does the draining itself through DoEncode, which runs the same ProcessOneOutput and therefore inherits the same slot-retirement and failure rules.

Why sync looks faster and is not. Saturated latency equals pipeline depth divided by throughput. At depth 4 and 740 fps that is 5.4 ms, which is what the async number measures; at depth 1 and 604 fps it is 1.66 ms. At a realistic 60 fps neither is saturated and the two are indistinguishable. Below 120 fps the dominant term is not the pipeline at all — it is GPU downclocking.
08

현재 설정을 읽어 고친 뒤 되돌려주는 편이 안전해. 그래야 다른 필드를 실수로 초기화하지 않아.

거절은 전부-아니면-전무다. [init] 필드가 하나라도 달라지면 InitOnlyFieldChanged를 반환하고 아무것도 적용하지 않아. 부분 적용으로 설정이 반쯤 어긋난 상태가 생기지 않아. 드라이버가 거절해도 이전 rate control 값으로 되돌려 놔. 비트레이트만 낮출 때는 forceIdr = false가 맞아 — IDR은 P프레임의 몇 배 크기라 혼잡한 상황을 더 악화시켜.

Part II · NvDecode · async pipeline

How an H.264 packet becomes a BGRA texture

같은 슬롯 링, 같은 게이트, 같은 완료 이벤트 구조다. 다른 건 세 가지 — NVDEC 는 push API 라 콜백이 호출 스레드에서 돌고, 완료 이벤트가 Win32 가 아니라 CUDA 이벤트이며, 프레임 수명이 콜백 반환이 아니라 ReleaseFrame 까지다.

DecodeThread CUDA stream (GPU) App (Acquire → render → Release) holds the context gate 
D3D11NvDecoder decoder;
decoder.Initialize(device, config, gate);
decoder.SetFrameCallback(OnFrame, this);   // frame 은 콜백 반환까지만 유효

DecodeFrameQueue queue(slotBytes, slotCount);
decoder.StartDecodeThread(&queue);         // 큐 펌프 가동

queue.EnqueueFrame(packet);                // 비트스트림 투입
// ...
decoder.Destroy();                         // 펌프도 같이 멈춘다
09

링은 같고, 계약이 다르다

엔코더처럼 m_writeSequence / m_readSequence 두 단조 카운터가 링을 돈다. 슬롯은 sequence & (m_outputSlotCount - 1) 로 얻고, 슬롯 하나가 텍스처 · CUDA 리소스 · 스테이징 버퍼 · 완료 이벤트를 전부 색인한다.

다른 점은 세 번째 상태가 있다는 것이다. 엔코더 슬롯은 비어 있거나 / NVENC 가 쓰는 중 둘 뿐이지만, 디코더 슬롯에는 앱이 들고 있는 중이 추가된다. 디코딩 결과는 D3D11 텍스처라 앱이 그걸 화면에 그리는 동안 디코더가 덮어쓰면 안 되기 때문이다.

슬롯 수는 2의 거듭제곱, 2 이상 32 이하. 색인이 & (count - 1) 이라 그렇다. 1 개는 특별히 막는다 — 앱이 한 장을 들고 있는 동안 쓸 슬롯이 없어져 전부 버려지기 때문이다. 기본값은 8 이고 NvDecConfig::outputSlotCount 로 바꾼다.
10

한 번 넣으면 콜백 셋이 그 자리에서 돈다

엔코더는 SubmitFrame 과 결과 수거가 서로 다른 스레드에 있다. 디코더는 그렇지 않다. cuvidParseVideoData 는 push API 라, 패킷 하나를 넣으면 파서가 호출한 스레드에서 콜백을 전부 돌린 뒤에 리턴한다. NVENC 의 enableEncodeAsync 같은 플래그는 NVDEC 에 없다.

11

대기는 어디로 갔나

"디코더는 동기식인가?" 라는 질문의 답은 아니오다. 다만 async 를 켜는 스위치가 있는 게 아니라, GPU 작업이 원래 비동기이고 코드가 그걸 쓰고 있는 것이다. 구조를 나란히 놓으면 같은 모양이다.

12

앱이 너무 많이 들고 있으면

슬롯보다 많은 프레임을 붙잡으면 디코더는 쓸 자리가 없다. 이때 아무 슬롯에나 덮어쓰면 앱이 렌더링 중인 텍스처가 찢어진다. 그래서 버린다 — 그리고 계속 버려지면 조용히 멈추는 대신 큰 소리로 죽는다.

임계값은 NvDecConfig::maxConsecutiveLostFrames (기본 32) 다. --hold 12 --dec-slots 8 로 재현한 실측: 8 장 전달 → 32 장 연속 유실 → OutputPoolExhausted 32회 → DecoderFaulted 1회. 종료 시점에 앱이 붙잡고 있던 프레임은 전부 반납되어 framesHeldByApp 이 0 으로 떨어진다.

13

디코더는 병목이 아니다

깊이 1 이라면 처리량에서 손해를 봐야 한다. 재보니 아니었다 — 모든 해상도에서 디코더가 엔코더 속도의 95~97% 를 따라간다. H.264 디코드가 엔코드보다 원래 훨씬 싸서, 깊이 1 로도 남아돈다.

출력 슬롯을 2 → 16 으로 늘려도 1080p 무제한 wall time 이 0.523 / 0.515 / 0.524 / 0.522 초로 완전히 평평하다. 슬롯은 출력 버퍼링일 뿐 디코드 병렬성이 아니라는 확인이다.

게이트 경합의 대가는 코덱이 치른다. 가짜 렌더 스레드가 초당 120회, 한 번에 4 ms 씩 (듀티 48%) 게이트를 가져가도 렌더 쪽 최대 대기는 0.002 ms 다. 엔코더도 디코더도 게이트를 짧게만 잡는다는 뜻이다. 대신 왕복 p50 이 2.79 → 3.38, p90 이 2.86 → 5.00 으로 늘어난다. UI 를 막지 않고 코덱이 지연을 흡수하는 쪽이므로 대화형 앱에는 이 방향이 맞다.

언제 다시 봐야 하나

display 스레드를 분리해 깊이를 늘리는 건 지금 이득이 0 이라 하지 않았다. 다음 조건에서는 다시 판단해야 한다 — 다중 스트림 동시 디코딩(깊이 1 이 세션 수만큼 누적), 4K 이상(디코드 비용이 엔코드에 근접), 디코드 후 무거운 후처리 추가. 신호는 간단하다. --dec-slots 스윕이 평평하지 않아지면 그때다.
