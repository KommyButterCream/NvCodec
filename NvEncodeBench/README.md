# NvEncodeBench

NVENC 엔코드 파이프라인의 회귀 테스트 + 성능 측정 하네스.

출력물은 `NvCodec.dll` 과 같은 폴더(`x64/<Configuration>/`)에 생성된다.

## 모드

```
NvEncodeBench selftest      회귀 케이스 실행 (종료코드 0 = 전부 통과)
NvEncodeBench [bench]       처리량 / 지연 측정 (기본 모드)
```

## 회귀 케이스

`selftest` 는 아래를 검증한다. 전부 실제 GPU 인코딩을 거친다.

| 케이스 | 검증 내용 |
|---|---|
| Bug B | `EncodeFrameQueue` 를 Shutdown 후 다시 Initialize 할 수 있다. Shutdown 이 큐에 남은 프레임을 생산자에게 반납한다 |
| Bug D | `frameCount`/`encodeBufferCount` 가 1 이거나 2의 n승이 아니면 초기화 단계에서 거절된다 |
| Bug C | 종료 시 in-flight 프레임이 전부 드레인되어 `submitted == completed`, 유실 0 |
| Bug A (1) | 단발성 출력 실패는 프레임 1장만 버리고 슬롯을 회수해 파이프라인이 계속 돈다. 앱에 `OutputReadFailed` 통지 |
| Bug A (2) | 실패가 연속 누적되면 조용히 얼어붙는 대신 `EncoderFaulted` 를 통지하고 pending 을 비운다 (종료가 20초 타임아웃에 매달리지 않음) |
| sync | `DoEncode` 동기 경로가 같은 슬롯 회수 규칙을 따른다 |
| guard | `EncodeThread` 가 동기 모드 엔코더를 거절한다. 이 조합은 아무도 출력을 드레인하지 않아 조용히 정지한다 |
| gate | Initialize / Destroy 가 게이트 안에서 돌고(각 1회 / 최대 2회), 게이트를 재귀 획득하지 않는다. 실제 게이트는 SRWLOCK Exclusive 라 재귀 시 데드락한다 |
| repeat | 같은 디바이스로 세션을 반복해 열고 닫아도 매번 전 프레임이 인코딩된다 |

출력 실패는 `D3D11NvEncoder::DebugFailNextOutputs()` 테스트 훅으로 주입한다.

## 측정 옵션

```
--width N --height N     해상도                      (기본 1920x1080)
--frames N               투입 프레임 수               (기본 600)
--fps N                  투입 속도, 0 = 무제한        (기본 60)
--buffers N              인코더 슬롯, 2의 n승 >= 2    (기본 4)
--queue N                큐 슬롯, 2의 n승 >= 2        (기본 4)
--pool N                 소스 텍스처 풀 크기          (기본 8)
--keyframe N             N 프레임마다 키프레임 요청   (기본 0 = 안 함)
--sync                   EncodeThread 없이 DoEncode 로 동기 인코딩
--callback-delay N       엔코딩 결과 콜백에서 N 마이크로초 동안 CPU 를 태운다.
                         앱의 브로드캐스트 작업(CPU 바운드)을 흉내내어
                         콜백 비용이 파이프라인에 주는 영향을 재기 위한 것
--fault-at N             N 번째 프레임에서 출력 실패 주입
--fault-count N          주입할 실패 횟수
--csv PATH               프레임별 지연/크기를 CSV 로 저장
```

`--fps 0` 은 앞서 넣은 프레임이 전부 인코더에 제출된 뒤에 다음 프레임을 넣어
드롭 없는 처리량 상한을 재도록 백프레셔를 건다. 큐 소비 카운트로는 게이팅할 수 없다 —
`EncodeThread` 는 인코더 슬롯이 없으면 프레임을 버리면서도 `ReleaseReadFrame()` 으로
"처리됨"으로 세기 때문이다. 그 손실은 리포트의 `dropped, no enc slot` 줄에 표시된다.

지연은 **큐 투입 -> 앱 콜백 도착** 구간이다. 스트리밍에서 실제로 의미가 있는 값.

## 사용 예

```
NvEncodeBench selftest
NvEncodeBench --width 1920 --height 1080 --fps 60 --frames 600 --keyframe 60
NvEncodeBench --fps 0 --frames 600                  (인코더 처리량 상한)
NvEncodeBench --sync --fps 0 --frames 300           (스레드 홉 없는 지연 하한)
NvEncodeBench --csv before.csv                      (개선 전 기준선 저장)
```

## 기준선 (RTX 5080, Release 빌드, 1080p, 2026-08-31)

개선 작업 전 측정값. A/B 비교 기준으로 사용한다.

### 포화 상태 (`--fps 0`) — 파이프라인 깊이의 대가

| 구성 | 처리량 | p50 | p90 | p99 |
|---|---|---|---|---|
| sync (DoEncode, 깊이 1) | 604 fps | 1.64 ms | 1.74 | 1.98 |
| async buffers=2 | 741 fps | 2.54 ms | 2.60 | 3.64 |
| async buffers=4 | 735 fps | 5.08 ms | 6.14 | 6.21 |
| async buffers=8 | 738 fps | 10.29 ms | 11.35 | 11.46 |

### 비포화 상태 (실제 동작점) — 투입 속도가 지배한다

| 투입 fps | p50 | min | 지연 원인 |
|---|---|---|---|
| 30 | 7.70 ~ 8.11 ms | 1.69 | GPU 다운클럭 |
| 60 | 3.68 ~ 5.04 ms | 1.71 | GPU 다운클럭 |
| 120 | 1.75 ms | 1.62 | 거의 없음 |
| 240 | 1.66 ms | 1.59 | 없음 |
| 480 | 1.60 ~ 1.92 ms | 1.54 | 없음 |

## 관찰 (측정으로 확인된 것)

**1. sync 가 async 보다 빠른 게 아니다.**
비포화 상태(60fps)에서 sync p50 3.691 ms, async p50 3.682 ms — 동일하다.
async 는 처리량 여유를 22% 더 준다(740 vs 604 fps). 지연 손실 없음.

**2. 포화 시 지연 = 파이프라인 깊이 / 처리량 (Little's Law).**
측정값이 거의 정확히 일치한다.

| 깊이 | 계산값 | 측정 p50 |
|---|---|---|
| 2 | 2 / 741 = 2.70 ms | 2.54 ms |
| 4 | 4 / 735 = 5.44 ms | 5.08 ms |
| 8 | 8 / 738 = 10.84 ms | 10.29 ms |

즉 `encodeBufferCount` 가 **부하 시 최악 지연을 직접 결정한다.**
처리량은 깊이 2~8 에서 726/735/738 fps 로 사실상 평평하므로,
저지연 목적이면 **깊이 2 가 8 보다 4배 유리하고 처리량 손실은 0**이다.
"버퍼 많을수록 안전" 이라는 직관과 반대다.
단, 깊이가 얕으면 일시적 스톨을 흡수하지 못해 프레임을 더 빨리 버린다.
원격 조작 용도라면 10 ms 늦게 도착하는 것보다 버리는 게 낫다.

큐 깊이(`queueFrameCount`)는 60fps 에서 2/4/8 모두 3.63~3.68 ms 로 무관하다.
인코더가 투입 속도의 12배 빠르면 큐에 프레임이 쌓이지 않기 때문.

**3. 30~60fps 에서 지연의 절반 이상은 GPU 전력 상태다.**
투입 속도를 올릴수록 지연이 줄고, `min` 은 모든 속도에서 1.6 ms 로 동일하다.
하드웨어는 항상 그 속도를 낼 수 있는데 느린 투입에서만 느려진다.
`nvidia-smi` 로 원인 확인:

| 투입 | SM 클럭 | 메모리 클럭 | 전력 | GPU 사용률 | p50 |
|---|---|---|---|---|---|
| 30 fps | 720~840 MHz | **810 MHz** | 30 W | 4 % | 8.11 ms |
| 480 fps | 2600~2640 MHz | **15001 MHz** | 61 W | 10 % | 1.92 ms |

메모리 클럭이 18.5 배 차이난다. 파이프라인이 대역폭 위주
(프레임당 CopyResource 8.3 MB + VideoProcessorBlt 읽기/쓰기)라 직접 영향을 받는다.

이건 코드로 고칠 수 없다. 배포 환경 설정 사항:
- NVIDIA 제어판 전원 관리 모드 = "최대 성능 우선"
- `nvidia-smi -lgc <min>,<max>` 로 클럭 하한 고정 (관리자 권한)

동시에, 대역폭이 병목이라는 뜻이므로 프레임당 여분의 풀프레임 복사를 제거하는
개선(P1)의 기대 효과가 다운클럭 상태에서 **더 커진다.**

**4. 콜백 예산은 이미 충분히 넓다. 별도 디스패치 스레드는 불필요하다.**

`--callback-delay` 로 콜백에서 CPU 를 태우며 측정한 결과.

포화 상태(`--fps 0`, buffers=4 queue=2):

| 콜백 지연 | 처리량 | p50 |
|---|---|---|
| 0 us | 723 fps | 5.13 ms |
| 100 us | 717 fps | 5.13 ms |
| 500 us | 722 fps | 5.10 ms |
| 1000 us | 726 fps | 5.11 ms |
| 2000 us | 488 fps | 8.02 ms |

**1000 us 까지 처리량이 전혀 떨어지지 않는다.** 완료 스레드는 프레임당
약 1.35 ms 를 `WaitForCompletionEvent` 에서 GPU 를 기다리며 놀고 있어서,
그 유휴 시간이 콜백 CPU 시간을 그대로 흡수한다. 2000 us 에서 그 여유를
넘어서면 처리량 = 1 / 콜백시간 으로 떨어진다.

실제 동작점(`--fps 60`)에서는 프레임당 16.7 ms 예산이 있어 여유가 훨씬 크다:

| 콜백 지연 | 처리량 | p50 | 슬롯 부족 드롭 |
|---|---|---|---|
| 0 us | 59.71 fps | 3.75 ms | 0 |
| 2000 us | 59.75 fps | 3.67 ms | 0 |
| 5000 us | 59.71 fps | 3.64 ms | 0 |
| 10000 us | 59.77 fps | 3.73 ms | 0 |
| 14000 us | 59.80 fps | 3.68 ms | 0 |

**14 ms 콜백까지 처리량/지연/드롭 모두 무영향.**

참고로 DesktopStreamingApp 의 `StreamingServer::BroadcastEncodedFrame` 은
청크당 풀 할당 + 32 KB memcpy + 뷰어별 enqueue 로, 뷰어 8 명 IDR 프레임(7 청크)
기준 100 us 내외로 추정된다. 60fps 예산 대비 **100 배 이상 여유**다.

따라서 비트스트림 링버퍼 + 디스패치 스레드는 이 앱에서 과잉 설계다.
콜백이 밀리초 단위로 무거워지거나(예: 콜백 안에서 블로킹 전송, 파일 I/O)
뷰어 수가 수십 단위로 늘어날 때 다시 검토한다.

**4-1. 슬롯 반납을 콜백 앞으로 옮긴 변경은 성능 개선이 아니다.**
`ProcessNextOutput` 에서 `RetireOutputSlot` 을 콜백보다 먼저 호출하도록 바꿨다.
처리량은 측정 오차 범위 내에서 동일했고(2000 us 에서 466 -> 488 fps),
포화 지연은 오히려 올라갔다(2000 us 에서 6.33 -> 8.02 ms).

지연이 올라간 이유는 명확하다. 이전에는 콜백 동안 슬롯이 묶여 있어
파이프라인이 설정된 깊이(4)를 다 쓰지 못했고, 그 우연한 스로틀이
지연을 낮추고 있었다. 이제는 깊이 4 를 온전히 쓴다 —
2000 us 케이스에서 4 / 488 = 8.2 ms 로 Little's Law 와 일치한다.

이 변경을 유지하는 이유는 성능이 아니라 **구조**다.
인코더 슬롯 점유 시간이 앱 콜백 소요 시간에 의존하지 않게 된다.
정상 상태 측정으로는 안 보이는 테일 이벤트(힙 경합, 페이지 폴트로 콜백이
드물게 수 ms 튀는 경우)가 슬롯 고갈로 번지지 않는다.
지연을 낮추고 싶으면 우연한 스로틀에 기대는 대신 `encodeBufferCount` 를
명시적으로 줄이는 것이 맞다(깊이 2 = 2.54 ms).

**4-2. 게이트 경합이 지연에 직접 실린다. 이게 가장 큰 남은 병목이다.**

`--contend-hz` / `--contend-us` 로 게이트를 점유하는 가짜 렌더 스레드를 붙여 측정.
1080p @60fps, buffers=4 queue=2, D3D11 multithread protection 없음:

| 렌더 부하 (점유율) | 처리량 | p50 | p90 | p99 | 슬롯부족 드롭 |
|---|---|---|---|---|---|
| 없음 | 59.85 fps | 3.66 ms | 7.30 | 9.33 | 0 |
| 60Hz x 2ms (12%) | 59.85 fps | 5.56 ms | 8.84 | 10.67 | 0 |
| 60Hz x 5ms (30%) | 59.87 fps | 6.70 ms | 11.15 | 12.82 | 0 |
| 120Hz x 5ms (60%) | 59.77 fps | 10.89 ms | 17.77 | 26.76 | 0 |
| 60Hz x 12ms (72%) | 59.78 fps | 17.49 ms | 26.55 | 35.61 | 0 |

데드락 없고 드롭 없고 처리량은 60fps 를 지킨다. 하지만 **지연이 렌더러의
게이트 점유율에 거의 비례해서 늘어난다**(72% 점유에서 3.66 -> 17.49 ms, 4.8 배).

엔코더가 게이트를 오래 잡는 것은 아니다. 경합 스레드가 게이트를 얻기까지
기다린 최대 시간은 0.2~1.6 ms 에 그친다. 반대로 엔코더가 프레임당 6 회
게이트를 요구하고, 그 매 회가 렌더러의 점유 시간만큼 밀린다.

완화 방향:
- 엔코더의 프레임당 게이트 획득 횟수를 줄인다(6 -> 2~3). 다만 한 번에 더 오래
  잡게 되므로 지연이 렌더러 쪽으로 옮겨간다. 공짜가 아닌 트레이드다.
  또한 게이트가 재귀 불가라 범위를 넓힐 때 중첩 획득에 주의해야 한다.
- **엔코딩용 D3D11 디바이스/컨텍스트를 분리하고 공유 텍스처로 넘긴다.**
  그러면 엔코드 경로에 게이트가 아예 필요 없어진다. 렌더러가 무거운 앱의
  구조적 정답이다.
- 렌더러가 없는 구성(현재 DesktopStreamingServer)에서는 이 항목이 문제되지 않는다.
  렌더 + 디코드를 함께 하는 클라이언트에서 문제가 된다.

**주의**: 리포트의 `gate acquisitions ... per submitted frame` 수치에는
경합 스레드의 획득도 포함된다. `contender acquires` 줄을 빼서 읽어야 한다.

**5. 게이트 획득이 프레임당 6회.**
Prepare / Convert / GetEncodedPacket(Lock+Unlock) / Map / Encode / Unmap.
CPU 비용 자체는 프레임당 약 180 ns 로 무의미하지만, 렌더 스레드가 있으면
획득 횟수만큼 대기 노출이 생긴다(4-2 참고).

## 측정 시 주의

- **반드시 Release 빌드로 측정한다.** Debug 는 값이 흔들려 오판을 유발한다.
- 30~60fps 측정은 GPU 전력 상태 때문에 런 간 편차가 크다(60fps 에서 3.68~5.04 ms).
  A/B 비교는 같은 투입 속도로 여러 번 돌려 비교한다.
- 코드 변경 효과를 보려면 `--fps 0` (포화, 편차 작음)과
  실제 동작점(`--fps 60`) 양쪽을 모두 재야 한다.
