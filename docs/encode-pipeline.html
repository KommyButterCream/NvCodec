NvCodec · NvEncode · async pipeline

How a BGRA frame becomes an H.264 packet

Three threads, one ring of slots, six gate acquisitions per frame. This traces the asynchronous path end to end, then shows the single edge that changes in synchronous mode.

Producer (capture) EncodeThread EncodeCompletionThread holds the context gate
01

The slot is the unit of everything

The encoder allocates encodeBufferCount slots. A slot number is not an index into one array — it indexes eight parallel arrays at once. Grasp this and the rest of the pipeline is bookkeeping.

02

Two counters chase each other

m_inputSequence and m_outputSequence are monotonic counters — they are never wrapped. Wrapping happens only where a slot is needed, in GetInputSlotIndex() and GetOutputSlotIndex(). Their difference is the number of frames NVENC still owes us.

03

Three threads, two handoffs

No thread polls another. Each handoff is a specific kernel object, and both were moved to the encoder's own lifetime so a thread teardown cannot invalidate a handle another thread is about to read.

04

Submit path — four gate acquisitions

Everything below runs on the EncodeThread. The producer's texture is copied into the pipeline immediately, which is what lets the queue slot go back to the capture engine before encoding has even started.

05

Drain path — the slot is freed before your callback

Everything below runs on the EncodeCompletionThread inside ProcessOneOutput. The ordering at the end is deliberate: the slot goes back into rotation before the app callback runs, so however long broadcasting takes, it never adds to encoder slot occupancy.

06

Where each failure goes

The distinction that matters: after the completion event fires, the hardware is done and the slot can be reclaimed, so a failure costs one frame. Before it fires, NVENC still owns the slot and there is nothing safe to do but give up the session.

Faulting is observable by design. EnterFaultedState clears m_acceptFrames, zeroes the pending bookkeeping so no waiter hangs on the 20-second timeout, and fires the error callback exactly once. From then on CanSubmitFrame() is deterministically false, so the app sees a hard stop instead of frames vanishing. Recovery is Destroy() then Initialize().
07

Synchronous mode changes exactly one thing

Passing enableAsyncPipeline = false removes the completion thread. Nobody else is added — the calling thread does the draining itself through DoEncode, which runs the same ProcessOneOutput and therefore inherits the same slot-retirement and failure rules.

Why sync looks faster and is not. Saturated latency equals pipeline depth divided by throughput. At depth 4 and 740 fps that is 5.4 ms, which is what the async number measures; at depth 1 and 604 fps it is 1.66 ms. At a realistic 60 fps neither is saturated and the two are indistinguishable. Below 120 fps the dominant term is not the pipeline at all — it is GPU downclocking.
